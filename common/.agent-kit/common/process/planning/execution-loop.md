## Implementation loop per phase

When a feature plan is `Ready` or `In Progress`, apply this loop after each phase and continue autonomously into subsequent phases and slices. One short update at each phase boundary (what shipped, what's next) — no per-tool narration, no per-phase approval. Two carve-outs stop the run: a design blocker (step 2) and `/feature-execute`'s decision checkpoint. A decision add-on the project turned on may settle a design blocker without the stop (step 2).

**Scope rule — applies to every step below.** "The phase's scope" is **every module the phase edited, plus any consumer module whose source references the edited API** (e.g. editing `<module-a>` while also editing `<module-b>` means both are in scope — and so does editing only `<module-a>` if `<module-b>` imports the changed classes). Code review, fixes, compile, and tests all run against the **full** scope — not just the primary module. Catching a break in a consumer module after the fact is the failure mode this rule exists to prevent.

**Dispatch rule — applies to every step below.** Each step is a dispatchable unit: run it inline or hand it to a same-harness subagent or a peer (`.agent-kit/common/process/dispatch/loop-steps.md`). Two invariants hold whatever the target: the **reviewer (steps 1/3) is always a fresh agent, never the instance that authored the code**, and the **checkpoint — commit + tag (6) + the phase-close re-stamp (7) — always stays with the orchestrator** (a dispatched step returns its diff; the orchestrator reads it — that read *is* the gate — then commits and re-stamps).

1. **Code review.** Spawn the appropriate code reviewer — the single-layer specialist when the phase touched only backend or only frontend, the full-stack reviewer when it touched both — scoped to every file the phase touched across all in-scope modules. Pass it the plan file path and the phase checklist so it judges against intent, not just style, and ask for its `Design concerns` section (`code-review.md`).
2. **Apply fixes.** Address non-design findings immediately, in whichever module they occur. A *design* concern — an entry in the review's `Design concerns` section, or a finding elsewhere that meets its definition (`.agent-kit/common/process/review/code-review.md`) — is the only thing that blocks progress: surface it to the user and wait. With a decision add-on on (`decision-addon.md`), `/feature-execute` hands it over first and follows the add-on's contract: it says when to surface the concern with the add-on's advice and wait, and when to apply the decision as a fix — after any test it names — and go on to step 3.
3. **Re-review.** Run the reviewer again on the updated files (still across all in-scope modules). Loop until it has no blockers or mechanical fixes left.
4. **Tests — author and run.** Tests are gradual: every phase that ships testable behavior (services, mappers, calculators, resources, validators, non-trivial logic) must include the tests that cover it, ticking the matching Test Plan bullets. Pure scaffolding with no testable behavior yet (config stubs, empty interfaces, build-file wiring) is an explicit exception — note it in the phase checkbox. **Compile and test every in-scope module.** Use the scoped test command from `.agent-kit-local/context/build-commands.md` for each in-scope module. Always run the **clean/fresh** variant so stale build output from before the edit can't mask a compile break. All green = green light to proceed. Failing or missing tests block the phase — do **not** defer test authoring to a later "tests" phase.
5. **Promote learnings & keep memory fresh.**
   - *Promote* — if a fix or refactor applied this phase **recurs** (you, or the code reviewer, recognize having made the same correction before), record it durably per `.agent-kit/modules/README.md` → "Promotion loop": a module-specific flow/contract/gotcha is **auto-written** to that module's memory under `.agent-kit-local/modules/<module>/`; a cross-cutting idiom is **proposed** for `design-principles.md`/`code-style.md` (the kit owner routes it: the stack's doc, or `.agent-kit/backend/`) and waits for confirmation. One-offs unlikely to recur are recorded nowhere — noise is the enemy. A promotion into a module the phase did not edit confirms nothing else there — that row keeps its stamp. A stack seed held by a repo that doesn't own its module is never written here: propose the line for the owning repo instead — written there, it reaches every consumer.
   - *Refresh the touched module's memory* — for each module this phase edited that has memory (`Documented` in `INDEX.md`, or — in the repo that owns it — a seeded dir with no row yet: give it its row now), size the upkeep to what changed. Outside per-phase upkeep: `_root` (`/module-extract root` owns it) and a stack seed held by a repo that doesn't own its module (it arrives by reinstall).
     - module has no memory → nothing.
     - memory exists, edit **not** memory-worthy (no change to public surface / SPI / flow / gotcha) → confirm every doc linked in its row still holds; the row is re-stamped in step 7.
     - memory exists, edit **was** memory-worthy → refresh that section now (the promote step above) and confirm the rest of the row; it is re-stamped in step 7.
     - UI edit touched a documented module → if `ui.md` exists, refresh it when UI surfaces, flows, or gotchas changed. If `ui.md` is absent and the phase produced non-obvious UI knowledge worth preserving, surface `/ui-extract <module>` as a follow-up, not an automatic write.
     - a doc in the row no longer holds beyond what this phase changed → fix that doc's content now, at `/module-extract`'s refresh weight (or `/ui-extract`'s), so the step-7 stamp stays true.

     This is cheap when the row was current — the source is already in context from doing the phase. A **whole-module re-extract is never automatic** (manual `/module-extract <module>`, after `--audit` shows large drift), and the whole-repo `--audit` sweep is never run per-phase.
6. **Checkpoint.** Once review is clean and tests are green, commit the phase's changes — step 5's memory refresh included, unstamped; kit paths the repo git-ignores stay out (step 7 → *Ignored kit*) — and tag the commit `<feature>/slice<N>/phase<M>` (lightweight tag, e.g. `git tag billing/slice1/phase1`). Gives a named restore point per phase without branch sprawl. When the phase's code lands in a **different repo** than the plan, tag the commit there **and** the plan repo's phase-close commit (step 7) with the same name — tools that read phase tags read only the plan's repo, so a phase tagged only elsewhere reads `NO DATA` and drops the whole feature from any per-phase calibration. Do **not** add a `Co-Authored-By` trailer — these commits are attributed to the human author only. Message style — subject shape and what the body carries — is `.agent-kit/common/process/authoring/doc-style.md` → *Commit messages*.
7. **Advance — one phase-close docs commit, every phase** (none where the repo git-ignores the kit).
   - *Tick* — tick the phase's checklist in the plan file and collapse the landed phase to its one-line outcome, **but keep its `Tier` / `Effort` / `Complexity` lines** — cost data, not instructions; `doc-style.md` → Plan files owns the rule, `Reviewer` and slice headers included.
   - *Re-stamp* — in the **same** commit, for every row step 5 confirmed, set **Verified** in `INDEX.md` **and every doc footer linked in that row** to the step-6 phase commit — never one without the other. It lives here because the phase commit doesn't exist until step 6. `.agent-kit-local/` sits outside the module dir, and a `(repo root)` module's drift excludes it (`INDEX.md` header), so this commit adds no drift of its own.
   - *Cross-repo* — when the phase's code lives in **another repo**, the stamp is that repo's step-6 commit, and that repo re-stamps the memory it holds in its own phase-close commit. In the plan repo, the phase-close commit carries the tick and gets the phase tag now (step 6); it re-stamps a copy the plan repo wrote itself, naming the owning repo beside the SHA, but **never a stack seed** — that arrives by reinstall.
   - *Kit-shipped memory* — in the repo that owns a module whose memory the kit ships (its name is in the stack's `stack.yml` → `modules:`; the stack's checkout is `.synced-from` → `stack_source:`, or `source:`'s `stacks/` for a stamp without it), copy every doc of that module this phase wrote — re-stamps included, footers naming this repo beside the SHA — to `<stack_source>/<stack>/modules/<name>/`, run `verify.sh <stack>` at the top level of that repo (`git -C <stack_source> rev-parse --show-toplevel`; no `verify.sh` there → say so in the phase update, never skip silently), and commit only those paths there. In that repo the memory is also a kit seed: unpromoted, the edit never reaches the other consumers, and a `--reset-defaults` reinstall reverts it. Consumers pick it up on their next reinstall. No checkout at that path → say so in the phase update, never skip silently.
   - *Ignored kit* — where the repo git-ignores the kit's paths, everything the loop writes there (step 5's memory, this step's tick and stamps) is still written but stays uncommitted: never force-add it (`git add -f`), whatever git's hint suggests. A cross-repo phase then has no plan-repo commit to tag; its tag stays on the code repo's commit.
   - ⚠ **Never skip or defer the re-stamp**, not even to batch it at slice end. A skipped stamp is how memory goes stale; a stamp over a row nobody confirmed is how it lies.

   Then move to the next phase.

Slice-boundary work — re-verification, Provisional promotion, header + `ROADMAP.md` updates — applies on top of this loop (`/feature-execute`).

## Code-anchor lifecycle for Reference content

When a phase ships, migrate its invariants from the plan's `## Reference` section into the codebase as doc comments (Javadoc / JSDoc / docstrings) on the relevant types/methods. Remove the migrated entry from the Reference.

⚠ Migrate the **invariant, not the prose**. It lands under `doc-style.md`'s comment budget, so compress it to the one line a future reader needs — this step must not become a pipe that turns plan verbosity into doc-comment verbosity. An entry too big to fit belongs in module memory instead.

**Diagrams have a different anchor.** A `### Shape` diagram describes what lives *between* files, so no doc comment can hold it, and it is **never pruned**: a `Done` plan file is *moved* to `archive/`, not copied (`.agent-kit/common/process/planning.md` → the folder lifecycle), so the plan stays the only copy of it for the file's life. What changes on `Done` is dispatch, not content — only the **active** slice's Shape ships to implementers (`.agent-kit/common/process/dispatch/reference-paste.md`); a `Done` slice's stays on the page but stops shipping. It may *also* be promoted into the touched module's memory (`modules/<module>/module.md` → *Non-obvious flows*) when a future reader of that module would ask the question it answers — only if it passes `.agent-kit/common/process/diagrams/diagrams.md` → *In module memory*; otherwise carry the lesson as prose. **Never into `architecture.md`** (Tier-0, always-on): if the feature changed the module *graph*, add the one line the graph needs. Promote by redrawing from the code that shipped — never by copy-pasting plan-time intent — during step 5 of the loop above, where the source is already in context.

**Reference carries only what module memory doesn't.** A fact that is durable and module-scoped belongs in that module's memory — promoted in step 5 above, then **deleted from the Reference**, which keeps a pointer to the module rather than a copy that drifts. The Reference's *Module memory in scope* rows are that pointer; a `Stub` module has no memory to point at, so its discovery stays in the Reference until someone runs `/module-extract`.

The Reference is a *frontier*: it carries invariants only for not-yet-implemented work. Code-anchored invariants survive the plan being archived, are discovered by future agents naturally during file reads, and don't have to be re-pasted into every dispatch prompt.

This shrinks the Reference over a feature's life. Towards the end of a multi-slice feature, the Reference should be near-empty: most invariants live in code, and only Pre-decided non-changes (which are fundamentally feature-meta, not code-anchorable) remain.
