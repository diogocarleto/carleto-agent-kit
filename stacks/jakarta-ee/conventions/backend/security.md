## Security

- **Validate at the resource layer only** — Bean Validation on Request DTOs via the validation groups (`api.md`). Services never receive raw unvalidated input.
- **Annotate every endpoint.** Every JAX-RS resource method carries an explicit `@RolesAllowed` or `@PermitAll` — the platform allows by default, so an unannotated method is a **public** endpoint and nothing warns you. Services assume an already-authorized caller.
- **Real deny-by-default is declarative.** A `web.xml` `<security-constraint>` over `<url-pattern>/*</url-pattern>` closes the deployment so a forgotten annotation fails *shut*. Without it the convention above is the only thing standing between a missed annotation and a public endpoint.
- ⚠ **Annotations cannot re-open what a constraint closed.** The container enforces the constraint *before* dispatch to the JAX-RS servlet, so a `@PermitAll` method under a closed `/*` gets 401 and JAX-RS never sees the call; annotations only narrow what the constraint already admitted. Re-opening a path takes a **second** `<security-constraint>` whose `<web-resource-collection>` narrows the `<url-pattern>` and that carries **no** `<auth-constraint>`. And a constraint matches URL pattern plus optional `<http-method>`, never a resource method — so a public GET and a role-restricted POST on one path cannot be split by one at all.
- **Never log** passwords, tokens, session ids, API keys or PII, at any level.
- **Never expose** stack traces, exception class names or server banners. The `ExceptionMapper` is the only place that shapes an error body; a 500 returns a correlation id and nothing else.
- **Secrets never reach a DTO.** A credential is write-only — accepted on a Request, never echoed on a Response. Never hardcode one; read deployment config injected once, not `System.getenv` at call sites.
- **Cryptography**: BCrypt or Argon2 for passwords, never MD5/SHA-1; AES-256 for symmetric encryption. Never roll custom crypto.
- ⚠ **`@RolesAllowed` on a plain CDI bean does nothing — on Jakarta EE 11 too.** The annotation carries no interceptor binding (`jakarta.annotation-api` 3.0.0 is the EE 10 declaration unchanged), and Jakarta Security 4.0 adds none — its only interceptor bindings are authentication ones (`@LoginToContinue`, `@RememberMe`, `@AutoApplySession`). **Nothing in either API artifact gives CDI a path to activate it on a plain bean**, and where it *is* honoured — on an Enterprise Bean, or on a JAX-RS resource method (below) — that is container wiring, not CDI. So never rely on it on a service (`patterns.md`). Authorization is checked at the resource boundary.
- ⚠ **Even there, enforcement is implementation-specific.** Jersey (Payara, GlassFish) applies `jakarta.annotation.security` on a resource method only when `RolesAllowedDynamicFeature` is registered; RESTEasy, CXF (TomEE) and Liberty need the deployment's security subsystem active. Where that wiring is missing the annotated endpoints are public **too** — so prove the rule with a `*ResourceTests` asserting 401/403, never by reading the annotation.
- ⚠ RUNTIME GAP — how a caller is authenticated, and how `jakarta.annotation.security` is wired into JAX-RS on this runtime (see the two rules above). Fill when the runtime is chosen; do not guess.
- ⚠ RUNTIME GAP — whether there is a `web.xml` at all. It is war-and-Servlet only, and both the profile (`architecture.md`) and the packaging, war vs runnable jar (`build-commands.md`), are still open; a Core Profile runtime has no Servlet container, so the two `<security-constraint>` rules above do not apply and the per-method annotations are the whole of it. Fill when the runtime is chosen; do not guess.
