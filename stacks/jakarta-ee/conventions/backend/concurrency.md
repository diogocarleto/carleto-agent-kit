## Concurrency

- **Never create a thread or an executor yourself** — no `new Thread(...)`, no `Executors.newFixedThreadPool(...)`, no `CompletableFuture.supplyAsync(task)` on the common pool. Concurrency comes from the container: `@Resource ManagedExecutorService`, `ManagedScheduledExecutorService`, or a `ManagedThreadFactory` when a library demands a factory. Give a workload its own `@ManagedExecutorDefinition` when it must not share the default pool.
- ⚠ **Injecting a managed executor takes a qualifier.** Concurrency 3.1 (the Jakarta EE 11 baseline) registers an `@ApplicationScoped` bean for a `@ManagedExecutorDefinition` **only when its `qualifiers` list is non-empty** — an empty list produces a bean for no injection point at all. Name the same qualifier on the definition and on the injection point. The other route the artifact names is your own `@Produces` for `ManagedExecutorService`, whose qualifiers must not conflict with a definition's non-empty list. So absent a producer, an unqualified `@Inject ManagedExecutorService` has nothing to satisfy it; reach the container's default executor by its JNDI name instead — `@Resource(lookup = "java:comp/DefaultManagedExecutorService")`.
- ⚠ **That `@Resource` needs a producer: it still cannot annotate a constructor parameter.** It targets types, fields and methods only, unchanged in the Jakarta EE 11 artifact — so injecting an executor with it directly forces field injection and stops the bean being `new`-able, breaking both `patterns.md` and `testing.md`. Bridge it with one `@ApplicationScoped` producer: an `@Resource(lookup = …)` field that `@Produces` the `ManagedExecutorService`. **A qualified definition needs no producer** — a qualifier you declare `@Target(… PARAMETER …)` is legal on a constructor parameter — which is the second reason to give a workload its own executor rather than sharing the default.
- ⚠ RUNTIME GAP — whether a runtime *also* publishes its default executor as an unqualified bean. The 3.1 artifact names `java:comp/DefaultManagedExecutorService` only as a JNDI name (it is the default of `@Asynchronous`'s `executor`), never as a CDI bean, so an unqualified injection resolving is a runtime's choice, not the API's promise. Confirm on the chosen runtime; until then, write the qualifier.
- ⚠ **An unmanaged thread carries none of the container's context.** A *managed* thread gets the classloader (`APPLICATION`) and the caller's security identity (`SECURITY`); a hand-made one gets neither — and the container never shuts the thread down, so it outlives redeploys. The failure surfaces under load, not in the test that made the pool.
- ⚠ **A managed thread does not carry the transaction.** `ContextServiceDefinition` defaults to `cleared = TRANSACTION`, so a task submitted inside a `@Transactional` method runs *outside* that transaction: the caller commits its own work, the task commits or fails separately, and nothing reports the split. Never submit a step that must be atomic with its caller.
- **Capture what a task needs before submitting it.** Read the request-scoped values, the caller's identity and the log correlation id into locals (or a record) at submit time. A task that reaches back into request state is guessing about propagation.
- ⚠ RUNTIME GAP — CDI request scope on a managed thread. Jakarta Concurrency defines exactly `APPLICATION`, `SECURITY`, `TRANSACTION` and `ALL_REMAINING` — unchanged in 3.1 — so request scope reaches the task only if the runtime supplies a `ThreadContextProvider` for it. Confirm on the chosen runtime; until then, write as if it does not.
- **`@Asynchronous` (`jakarta.enterprise.concurrent`) belongs on a CDI bean method** returning `CompletableFuture`, `CompletionStage` or `void`, and must be called through an **injected reference** — a self-call on `this` is not guaranteed to be intercepted, and an un-intercepted `@Asynchronous` method simply runs inline (`patterns.md`). Use `jakarta.ejb.Asynchronous` only where the class is already an EJB; never both in one project.
- **Consume every future.** An exception inside a submitted task is held in its `Future` and reported nowhere else — a discarded future is a silently swallowed failure. Either join it, or attach a handler that logs.
- **`@ApplicationScoped` beans are singletons** — fields must be stateless or effectively immutable. Never share mutable state between requests; per-request state belongs in a `@RequestScoped` bean or a method local.
- ⚠ **An in-JVM lock is not a cluster lock.** `synchronized` and `ReentrantLock` coordinate one instance; with more than one replica they guarantee nothing, and the resulting corruption reads like bad data rather than a race. Cross-instance mutual exclusion needs shared state — see `persistence-<db>.md`.
- **Blocking I/O is fine on a managed thread** — the container sizes the pool for it. Long CPU-bound work is not: give it its own executor so it cannot starve request handling.
